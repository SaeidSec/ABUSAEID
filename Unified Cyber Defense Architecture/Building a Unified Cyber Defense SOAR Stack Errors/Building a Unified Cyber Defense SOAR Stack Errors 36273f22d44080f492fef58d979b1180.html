3. Problem 1: Cortex Analyzer Fails — python3: No such file or directory

Symptom

Every time an OpenCTI or MISP analyzer was run from the Cortex UI, it returned:

json

{
"errorMessage": "env: 'python3': No such file or directory",
"input": null,
"success": false
}

This affected all locally deployed analyzers:

  • OpenCTI_v6_SearchExactObservable_2_0
  • OpenCTI_v6_SearchObservables_2_0
  • OpenCTI_SearchExactObservable_2_0
  • OpenCTI_SearchObservables_2_0
  • MISP_2_1

Root Cause

Cortex 4.0.0 supports three job runner modes:

  1. Docker runner — spawns a dedicated Docker container per analyzer job
  1. Process runner — runs the analyzer script directly using local Python
  1. Kubernetes runner — for K8s environments

The application.conf had no job.runner configuration, so Cortex defaulted to process runner, which tried to execute python3 directly inside the Cortex JVM container — where Python is not installed.

Evidence

From Cortex container logs:

[warn] o.t.c.s.JobRunnerSrv - The package cortexutils for python hasn't been found
[warn] o.t.c.s.JobRunnerSrv - The package cortexutils for python2 hasn't been found
[warn] o.t.c.s.JobRunnerSrv - The package cortexutils for python3 hasn't been found
[info] o.t.c.s.ProcessJobRunnerSrv - Execute /opt/cortexneurons/analyzers/OpenCTI/opencti.py
[info] o.t.c.s.ProcessJobRunnerSrv - Job xxx: env: 'python3': No such file or directory

Investigation Steps

bash

# Step 1: Confirm Python3 doesn't exist inside Cortex container
docker exec -it cortex which python3
# Returns nothing — confirmed missing

# Step 2: Confirm Docker socket IS accessible
docker exec -it cortex docker ps
# Returns container list — Docker IS available

# Step 3: Check existing application.conf for runner config
grep -i "job\|docker\|runner" /home/saeidsec/SOAR_LABS/docker/testing/cortex/config/application.conf
# Returns only: cache.job = 10 minutes
# No runner config found — ROOT CAUSE CONFIRMED

Solution

Add job runner configuration to application.conf:

bash

nano /home/saeidsec/SOAR_LABS/docker/testing/cortex/config/application.conf

Add at the bottom:

hocon

# Job runner configuration - use Docker to run analyzers
job {
runner = [docker, process]
}

docker {
pullImage = false
}

Key points:

  • runner = [docker, process] — try Docker first, fall back to process
  • pullImage = false — use locally built images, don't attempt Docker Hub pull

4. Problem 2: Missing Job Runner Configuration



Symptom


Even after adding job.runner, analyzers still failed because Cortex did not know which Docker image to use for each analyzer.

Log evidence:

[warn] o.t.c.s.JobRunnerSrv - worker xxx can't be run with docker (doesn't have image)
[info] o.t.c.s.ProcessJobRunnerSrv - Execute /opt/cortexneurons/analyzers/OpenCTI/opencti.py

Root Cause

The analyzer JSON definition files lacked the dockerImage field. Cortex Docker runner requires this field to know which image to instantiate per job.

Before (missing field):

json

{
"name": "OpenCTI_v6_SearchExactObservable",
"version": "2.0",
"command": "OpenCTI/opencti.py",
...
}

After (correct):

json

{
"name": "OpenCTI_v6_SearchExactObservable",
"version": "2.0",
"command": "OpenCTI/opencti.py",
"dockerImage": "cortexneurons/opencti:latest",
...
}

Solution — Step 1: Build Docker Images for Analyzers

The OpenCTI analyzer already had a Dockerfile. Build it:

bash

cd /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/OpenCTI
docker build -t cortexneurons/opencti:latest .

OpenCTI Dockerfile (existing):

dockerfile

FROM python:3-alpine
WORKDIR /worker

ARG REQUIREMENTS=requirements.txt

RUN apk add --no-cache file-dev

COPY requirements*.txt OpenCTI/
RUN test ! -e OpenCTI/${REQUIREMENTS} || pip install --no-cache-dir -r OpenCTI/${REQUIREMENTS}
COPY . OpenCTI/

ENTRYPOINT ["python", "OpenCTI/opencti.py"]

Solution — Step 2: Add dockerImage to All JSON Configs

bash

cd /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/OpenCTI

python3 -c "
import json
files = [
'OpenCTI_SearchExactObservable.json',
'OpenCTI_SearchObservables.json',
'OpenCTI_v6_SearchExactObservable.json',
'OpenCTI_v6_SearchObservables.json'
]
for f in files:
with open(f) as fp:
data = json.load(fp)
data['dockerImage'] = 'cortexneurons/opencti:latest'
with open(f, 'w') as fp:
json.dump(data, fp, indent=2)
print(f'Updated {f}')
"

Verify:

bash

grep "dockerImage" OpenCTI_v6_SearchExactObservable.json
# Output: "dockerImage": "cortexneurons/opencti:latest"

5. Problem 3: Responder Path MalformedURLException

Symptom

Cortex logs showed on every startup:

[warn] o.t.c.s.WorkerSrv - Worker path (/opt/cortexneurons/responders) is not found
java.net.MalformedURLException: no protocol: /opt/cortexneurons/responders

Root Cause

Two issues combined:

  1. The responders directory did not exist on disk
  1. The application.conf was passing a bare filesystem path /opt/cortexneurons/responders in the urls array, which expects either a full URL (https://...) or a file:// URI — not a raw path

Solution — Step 1: Create Responders Directory

bash

mkdir -p /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/responders
touch /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/responders/.gitkeep

Solution — Step 2: Fix URL Format in application.conf

Before (broken):

hocon

responder {
urls = [
"https://download.thehive-project.org/responders.json"
"/opt/cortexneurons/responders"
]
}

After (fixed):

hocon

responder {
urls = [
"https://download.thehive-project.org/responders.json"
"file:///opt/cortexneurons/responders"
]
}

Same fix applied to the analyzer section:

hocon

analyzer {
urls = [
"https://download.thehive-project.org/analyzers.json"
"file:///opt/cortexneurons/analyzers"
]
}

6. Problem 4: MISP Analyzer Has No Dockerfile

Symptom

When attempting to build the MISP analyzer Docker image:

bash

docker build -t cortexneurons/misp:latest .
# Error: unable to prepare context: unable to evaluate symlinks in Dockerfile path:
# lstat /home/.../analyzers/MISP/Dockerfile: no such file or directory

Root Cause

Unlike the OpenCTI analyzer, the MISP analyzer directory from the Cortex-Analyzers repository did not ship with a Dockerfile. The directory contained only:

MISP/
├── MISP.json
├── README.md
├── assets/
├── misp.py
├── mispclient.py
└── requirements.txt

Solution — Create MISP Dockerfile

bash

cat > /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/MISP/Dockerfile << 'EOF'
FROM python:3-alpine
WORKDIR /worker

RUN apk add --no-cache file-dev

COPY requirements.txt MISP/
RUN pip install --no-cache-dir -r MISP/requirements.txt

COPY . MISP/

ENTRYPOINT ["python", "MISP/misp.py"]
EOF

Build the image:

bash

cd /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/MISP
docker build -t cortexneurons/misp:latest .

Add dockerImage to MISP JSON:

7. Problem 5: dockerImage Field Missing in Analyzer JSON

Symptom (Recurring)

Even after adding dockerImage to JSON files and building images, analyzers still logged:

[warn] o.t.c.s.JobRunnerSrv - worker xxx can't be run with docker (doesn't have image)

Root Cause — Deep Analysis

This was the most subtle issue. Cortex 4.0.0 stores analyzer worker configurations in Elasticsearch when an analyzer is first enabled via the UI. Subsequent restarts read from this cached DB record — not from the JSON files on disk.

This means:

  1. You add dockerImage to JSON on disk ✓
  1. You restart Cortex ✓
  1. Cortex reads analyzers from disk into memory for display ✓
  1. But when a job runs, it reads the worker config from Elasticsearch — which was cached before you added dockerImage ✗

Proof from logs:

# When job runs — reads stale ES record, no dockerImage found:
[warn] worker xxx can't be run with docker (doesn't have image)
[info] ProcessJobRunnerSrv - Execute /opt/cortexneurons/analyzers/OpenCTI/opencti.py
# Falls back to process runner → python3 not found → failure

# But VirusTotal (enabled AFTER dockerImage standard was set) worked fine:
[info] DockerClient - about to start container 95d5bf49...
[info] Job LDXzLJ4BJ_Ze71K-KUWk has finished with status Success

Solution — Force Re-read from Disk

The fix is to disable and re-enable the analyzer in the Cortex UI. This deletes the stale Elasticsearch record and creates a fresh one from the current JSON file on disk.

Steps:

  1. Go to Cortex UI → Organization → Analyzers
  1. Find OpenCTI_v6_SearchExactObservable → click toggle to DISABLE
  1. Wait 5 seconds
  1. Click toggle to ENABLE → fill credentials → Save
  1. Repeat for every OpenCTI and MISP analyzer variant

Analyzers to cycle:

  • OpenCTI_SearchExactObservable
  • OpenCTI_SearchObservables
  • OpenCTI_v6_SearchExactObservable
  • OpenCTI_v6_SearchObservables
  • MISP

After re-enabling, the Docker runner correctly picks up the image:

[info] DockerClient - about to start container c667d8491c17...
volumes: /tmp/cortex-jobs/cortex-job-xxx
[info] DockerClient - container started and awaited with code: 0
[info] Job xxx has finished with status Success

8. Problem 6: Cortex Uses Stale Cached Analyzer Configs

(This was the same root cause as Problem 5 but manifested in a different way — Cortex reporting 404 on analyzer endpoints.)

Additional Symptom

[warn] o.t.c.s.ErrorHandler - GET /cortex/api/analyzer/MISP_2_1 returned 404
[warn] o.t.c.s.ErrorHandler - GET /cortex/api/analyzer/OpenCTI_v6_SearchExactObservable_2_0 returned 404

Root Cause

TheHive was calling Cortex API endpoints using the analyzer IDs it had previously cached. After Cortex restarts with config changes, the internal analyzer registration IDs can shift, causing 404s.

Solution

Same as Problem 5 — disable/re-enable analyzers in Cortex UI forces fresh registration. Also ensure TheHive's Cortex connector is properly configured with the correct API key:

In TheHive application.conf:

hocon

cortex {
servers = [
{
name = "Cortex"
url = "http://cortex:9001"
auth {
type = "bearer"
key = "YOUR_CORTEX_API_KEY"
}
}
]
}

9. Problem 7: MISP SSL Certificate Verification Failure

Symptom

After Docker runner was working, MISP analyzer jobs ran but failed with:

ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED]
certificate verify failed: self-signed certificate (_ssl.c:1081)

pymisp.exceptions.PyMISPError: Unable to connect to MISP
(https://192.168.0.101:8443/).
HTTPSConnectionPool: Max retries exceeded with url: /servers/getVersion
(Caused by SSLError)

Root Cause

MISP was deployed with HTTPS using a self-signed certificate. The MISP analyzer Docker container tried to verify this certificate against known CAs — which fails for self-signed certs.

The cert_check = false config option in Cortex UI was set, but the mispclient.py code was using the older ExpandedPyMISP class (now deprecated) which had different SSL handling behavior in newer PyMISP versions.

Solution — Two-Part Fix

Part 1: Fix in Cortex UI (MISP Analyzer Config)

In Cortex UI → Organization → Analyzers → MISP → Edit:

cert_check → false
url → ["https://192.168.0.101:8443"]
key → ["YOUR_MISP_API_KEY"]

Disable and re-enable the analyzer after saving.

Part 2: Fix in TheHive MISP Connector

In TheHive UI → Administration → Platform → Connectors → MISP → Edit:

  • Check Certificate Authority → Toggle OFF
  • Disable hostname Verification → Toggle ON
  • Click Update

Part 3: Force SSL=False in mispclient.py (if above insufficient)

bash

# Inspect current SSL handling
grep -n "ssl\|verify\|cert" \
/home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/MISP/mispclient.py

# Force disable SSL verification
sed -i 's/ssl=verify/ssl=False/g' \
/home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/MISP/mispclient.py

# Rebuild Docker image
cd /home/saeidsec/SOAR_LABS/docker/testing/cortex/neurons/analyzers/MISP
docker build -t cortexneurons/misp:latest .

# Disable/re-enable MISP in Cortex UI to load new image

Result: MISP analyzer jobs now succeed:

[hash] 6a9bc3a1eb4f... → MISP_2_1 → Success ✅
[other] KRYPTON → MISP_2_1 → Success ✅

12. Lessons Learned

1. Cortex Job Runner Must Be Explicitly Configured

Cortex 4.0.0 does not default to Docker runner even when the Docker socket is mounted. Always add job { runner = [docker, process] } to application.conf.

2. dockerImage Field is Mandatory for Docker Runner

Every analyzer JSON definition must include "dockerImage": "imagename:tag" for Cortex to use the Docker runner for that analyzer.

3. Elasticsearch Caches Analyzer Configs

Editing JSON files on disk is not enough. The UI registration (enable/disable cycle) is required to push changes to Elasticsearch where job execution reads from.

4. File URL Protocol Required for Local Paths

Cortex URL arrays expect proper URIs. Local paths must use file:///path format — bare paths cause MalformedURLException.

5. Missing Directories Cause Silent Failures

The responders directory must exist even if empty. Cortex will log warnings and potentially degrade if referenced directories are missing.

6. Self-Signed SSL Requires Explicit Bypass

Both the Cortex analyzer config (cert_check = false) and the PyMISP client code (ssl=False) must have SSL verification disabled when connecting to services with self-signed certificates.

7. Docker Runner Confirmation

To confirm Docker runner is being used (vs process runner), watch docker events while triggering jobs. You should see container create/start events. If you see ProcessJobRunnerSrv in logs, Docker runner is NOT being used.

8. Disable/Re-enable Cycle is the Universal Fix

Whenever analyzer behavior doesn't match expectations after config changes, disable and re-enable in Cortex UI. This forces a fresh read from JSON and fresh write to Elasticsearch.
